# SQLite 按记录存储升级

此次升级保持单实例运行。用户、登录会话、供应商配置、白名单和任务分别按记录写入 SQLite。课程课节和助教草稿分别按课节、按提交存储。作业快照和其他整体读写的记录保留为独立文档。媒体与笔记成品仍由文件系统保存。

## 维护窗口前

1. 从生产取得数据库与关联数据文件的一致副本，放在隔离目录。数据库运行中备份使用 SQLite Online Backup API 或 `VACUUM INTO`。任务文件、课节文件、密钥和发布日志需和数据库对应同一个时间点。
2. 在副本的服务工作目录运行新版 `assistant-server --migrate-db`。命令取得实例锁，升级当前目录的 `data/assistant.sqlite3`，补导仍只有旧文件的课节索引和助教草稿，最后检查数据库并输出 SQLite 版本、迁移版本和行数。命令会写入当前目录的数据，预演时确认目标是副本。
3. 核对升级前后的用户、有效会话、白名单、每个账户的希元和加速券、支付订单、任务状态、课节顺序、TeX 文件和助教草稿。已同步和登分结果不确定的草稿应保留原状态。首次迁移出现重复邮箱、无效数据或主密钥错误时应先处理数据，避免在现场手改数据库。
4. 测量备份、迁移、核对和回滚耗时。用同样的数据压测鉴权、登录写入和任务历史。六小时窗口应留出实测所需的恢复预留时间。
5. 如供应商 API Key 由部署环境管理，将 Base64 编码的 32 字节随机主密钥作为 `ASSISTANT_PROVIDER_KEY` 注入预演和新版服务。未配置时，仅在需要保存供应商密钥时生成 `data/provider-key.bin`。升级和日常运行使用同一份主密钥，将其单独保管并纳入恢复演练。Windows 部署限制数据目录 ACL。旧快照和旧集合可能仍有历史明文，按敏感数据保管。

## 切换

1. 暂停入口和新任务，停旧服务并确认没有写入进程。与支付中心核实回调重试和未结算订单的对账方式。
2. 做同一批次的完整备份，包含生产 `data/`、`course_data/`、业务使用的外部数据目录和部署密钥。归档旧程序与配置。
3. 在真实服务工作目录运行 `assistant-server --migrate-db`。核对命令退出状态、记录数量、现有未结算任务和依赖的文件。旧数据库的 `collections` 保留用于核对。导入完成后，`whitelist.json` 仅作旧数据留档，使用管理后台修改白名单。
4. 在入口仍受控时启动新版，用现有会话验证登录、任务历史、笔记下载和后台。确认没有待处理的迁移错误再开放写入。监控连接等待、持锁时间、错误率和支付对账。此版本继续用单连接，未启用多连接 WAL。

## 回滚

- 开放写入前，停新版并恢复同一批次的数据库、关联文件和密钥，再启动旧版。
- 开放写入后，先冻结入口并备份新版数据，清点新增会话、撤销、订单、扣费和交付结果。优先修复新版；需要回退时先完成增量对账与回放，旧程序无法读取新版写入的业务表。
